Milestone 23 Review & Milestone 24 Plan

Sprint ran 20 – 31 July 2026 · Milestone 24 opens 3 August · Team of 3 · Prepared for the CEO & COO

This was a foundations sprint, and it went well. We deliberately spent the fortnight on the platform underneath Katch Cloud rather than on new customer features — and we closed 91% of it, our third strong sprint in a row. The framework the whole application runs on is now current, our test suite is fully automated, and the production databases moved to a supported version two days before a new AWS charge would have started.

The one thing that needs a decision. Everything built this sprint is merged but not yet released to production — 56 changes are queued behind a release that hasn't been cut since 20 July. That release is the largest of the year and needs a planned window. It is the main topic for Milestone 24.

What we shipped

Five things worth knowing about, in plain terms.

1. The application framework is current again Done

Katch Cloud moved to Symfony 8, PHP 8.4 and Doctrine 3 — the three components the entire backend is built on (konvoy #5512). This had been deferred for some time. Alongside it we restored our distributed tracing on the new version (#5531) and fixed two problems the upgrade exposed in how the database schema is read (#5471, #5620).

Why it matters: we were drifting towards unsupported versions of our core dependencies. Being current means security patches keep arriving, hiring is easier, and the next upgrade (PHP 8.5, now in discovery) is a small step rather than another large project.

2. Manual test tooling retired — automated tests now gate every release Done

We finished migrating end-to-end testing from Rainforest to Playwright and switched Rainforest off (#5231, #5234). Playwright is now the required check before anything reaches production, and the suite also runs overnight with failures posted straight to Slack.

Why it matters: removes a third-party subscription, removes manual test maintenance, and means regressions are caught before release rather than reported by staff or customers. One small tidy-up task remains — archiving 35 old tests in the retired tool.

3. A batch of speed and stability fixes Done

We removed four cases where loading organisation and customer data triggered hundreds of separate database queries instead of one (#5159, #5354, #5552). We also fixed a fault where every database query failed if a monitoring component was unavailable (#5521), stopped keg activity logs getting permanently stuck mid-process (#5559), and cut a stream of false alerts that had been masking real ones (#5522).

Why it matters: the organisation pages get faster for everyone, and our alerting becomes trustworthy again — which is what lets us find real problems quickly.

4. Orders and contract-brewer pricing improvements Done

The customer-facing work this sprint: email status now visible directly on the Orders table and order page (#4369), a Collection Request detail page (#4447), location details in the side panel (#4427), and orders now prevented from mixing locations across countries (#4415). On pricing, contract-brewer freight is now calculated from the delivery location, so new contract-brewer customers no longer need a manual account link set up by hand (#5568), and Venue Collection pricing became editable on casual customer agreements (#5562).

Why it matters: the freight change removes a manual onboarding step per contract-brewer customer. The rest reduces the "where is my order up to?" questions that come back to the operations team.

5. Booths transport integration progressed Continuing

Four pieces of the Booths EDI integration landed: automatic order submission when an order is scheduled, a reconciler that checks Booths' response and alerts on failure, the per-location configuration screen, and submission status exposed back into the order views (epic #5044, #5631).

Why it matters: this is the automated hand-off of orders to a transport provider. The remaining step is not ours — it needs Booths-side coordination to complete (#5051). Worth knowing who is chasing that.

The production database upgrade

Unplanned, urgent, done on 2 August — and the largest single cost item of the quarter.

What happened. MySQL 8.0 — the database version running every Katch Cloud production region — left standard support on 31 July 2026. From 1 August, AWS begins charging "Extended Support" automatically, per database, per hour, for the privilege of staying on it. There is no opt-out other than upgrading.

Why it had to happen immediately. The charge started the moment support ended. Every day on the old version cost real money for nothing in return, so this jumped the queue ahead of the planned September schedule. All four environments — development plus the Australian, European and North American production regions — were upgraded to MySQL 8.4 on 2 August. The three production regions went in a single window with under three minutes of downtime each, and every pre-flight check passed first time. It landed roughly seven weeks ahead of plan.

The remaining $253/month sits on a single leftover development database. It is being retired as soon as one dependent fix lands, which is days rather than weeks. The database is now on a version supported until 2032, and all health, backup and performance checks came back clean.

An honest framing for the P&L. This is avoided cost, not a saving. It does not reduce the current AWS bill — it prevents a new $1,904/month charge that would otherwise have started on 1 August and continued indefinitely. Total AWS spend for July was $10,036 AUD against an April baseline of $9,451 and a target of $7,200, so the headline number has not come down yet. Bringing it down depends on the remaining phases of the cost programme, not on this piece of work. What this did was stop the number going up by a fifth.

Four things to watch

Stated plainly, with what would help.

1. Release debt is the biggest risk we carry

No release has gone out since 20 July, and the infrastructure side has an equivalent gap tracked since June. The longer the queue, the harder it is to tell which change caused a problem if one appears. The framework upgrade being in that queue makes it higher-stakes than usual.

What would help: agreement on a release window in the first week of M24, and acceptance that the sprint carries less new feature work because of it.

2. An open production fault, unrelated to the upgrade

Four background processing components have been restarting roughly every eleven minutes across all three production regions for eleven days. It was found during pre-flight checks for the database work. Customer impact appears limited so far, but it is unresolved and it is noisy enough to hide other faults.

What would help: nothing from you — flagging it so it isn't a surprise if it escalates.

3. A rollback window on the database upgrade closes 6 September

There is no way to downgrade from MySQL 8.4. Two of the three production regions do not have a permanent pre-upgrade backup, only a temporary one that expires. Making it permanent is a five-minute, zero-downtime task and it is being done today.

What would help: nothing — noted for completeness because the deadline is real.

4. Booths is waiting on Booths

Our side of the transport integration is largely built. Completing it needs coordination from Booths that is outside engineering's control, and it has been open for a while.

What would help: confirmation of who owns the Booths relationship and is chasing it, so engineering isn't holding a half-finished integration indefinitely.
