Board Configuration Runbook

How the Konvoy Cloud board is meant to be wired, why each field exists, and the exact steps to get there. Companion to the Sprint Hygiene Runbook — that one is the weekly cadence, this one is the wiring underneath it. Tick boxes save locally; your progress survives a refresh.

One-time migration. Run it once, tick the boxes, done. UI steps need clicking — the public API can't make them. API steps are scriptable and the snippet is inline. DONE steps were executed on 2026-08-18 during the configuration review; they're here for the audit trail.

Two rules follow from it: (1) An issue and its PR are independent objects — closes #5745 is a reference, not containment, and nothing propagates across it. The fix is automation and omission, not diligence. (2) Milestone means scope. Sprint means time. They are not two views of the same thing.

2. Rebuild the Epics view as a grouping UI

▾

The current Epics view filter is -no:parent-issue minus a hand-typed exclusion list of 17 parent issue numbers. There are 27 open epics — so 10 are invisible, and the list needs editing whenever an epic is created or finished.

Open the Epics view

Set Group by → Parent issue (the field already exists)
Add Sub-issues progress as a visible column for the completion bars
Exit criteria: All 27 epics appear, grouped, with no hardcoded issue numbers anywhere in the view config. The view stays correct when epic #28 is created.

Standing rules

▾
  • Theme-named milestones are correct and stay — Billing in Konvoy Cloud, LaunchDarkly Feature Flags, Vercel Setup Audit, Konvoy End-User Documentation. Big epics get a theme name, never an M##.
  • Stop creating M## milestones. The Sprint iteration field does this job and auto-advances.
  • PRs stay out of milestones — one exception: a release payload milestone answering "what shipped in v1.89.x".
  • Never delete a milestone — close it. Closed milestones keep their attached issues, which is what the sprint reports read from.

The four saved searches

▾

Bookmark these. They replace what the milestone page was giving you, and they reach the whole backlog.

Creating an epic

▾
Create the parent issue, title prefixed [EPIC], issue type Epic
Add children as sub-issues — not a checklist, not a new milestone, not a new project
Give the epic a theme-named milestone if it's a stakeholder-visible programme; otherwise no milestone at all
Leave the children's Sprint field empty until they're actually planned in
Do not set the project on the children — Auto-add sub-issues to project handles it
Exit criteria: The epic shows an n/m sub-issue bar. The 14 new children have not pushed anything down a list you care about, because your triage search excludes them.

What not to do

▾
No project-per-epic

27 epic boards means 27 places to look and no portfolio rollup. Those 9 workflows plus Status / Priority / Size / Story Points / Cost Initiative would need recreating and maintaining per project. Status vocabulary drifts immediately and "Done" stops meaning one thing. Projects are for workstreams; scope units are what sub-issues are for — you already have that, #5835 reads 13/13.

No milestone-per-sprint

See the Milestones tab. Sprint milestones are a workaround from before the iteration field existed, and they're the field the epic milestones have been fighting over.

No epic label once the issue type lands

Two markers for one concept means neither is trusted. The label already finds 8 of 27.

Run these alongside the Sprint Hygiene Runbook blocks. The Sprint field is 14-day, Monday start — currently M29 (17–28 Aug) and M30 (31 Aug–11 Sep).

Snapshot script API

▾

Counts the things the REST search endpoint gets wrong. Run before each report.

gh api graphql --paginate -f query=' query($endCursor:String){repository(owner:"konvoy-kegs",name:"konvoy"){ issues(first:100,states:OPEN,after:$endCursor){ pageInfo{hasNextPage endCursor} nodes{number parent{number} subIssues(first:1){totalCount} milestone{title}}}}}' \ --jq '.data.repository.issues.nodes[]' | python3 -c ' import sys,json r=[json.loads(l) for l in sys.stdin if l.strip()] print("open ",len(r)) print("epic children ",sum(1 for i in r if i["parent"])) print("triage (no parent)",sum(1 for i in r if not i["parent"])) print("epics ",sum(1 for i in r if i["subIssues"]["totalCount"])) print("no milestone ",sum(1 for i in r if not i["milestone"]))'
Run after Setup, then once a month. If you can't tick all of these, something drifted.

Why the fields feel like double entry

Because they are two objects. GitHub models an issue and a pull request as independent items that happen to reference each other. closes #5745 creates a link for closing behaviour and nothing else — no field propagates across it. So the instinct that you're doing the same work twice is correct; the mistake is concluding that the fix is to be more diligent. The fix is that one of those fields should be automatic and the other shouldn't exist on a PR at all.

Project membership is automatable and already automated. Nine workflows are enabled on Project 4 including Auto-add to project, Auto-add sub-issues to project, Pull request linked to issue and Pull request merged. The only reason you've been setting the project on PRs by hand is that the auto-add filter was written for issues. One filter edit and the step is gone permanently.

Milestones have no workflow. There isn't one in the built-in list and nothing in .github/workflows touches them. That's deliberate on GitHub's part — the PR milestone was designed for release payloads ("what shipped in v1.89.4"), which is a genuinely different question from "which sprint was this in". It's the one place a PR milestone earns its keep, and you already run a release process that could use it.

Why the morning list felt unmanageable

It's a view problem wearing a data-model problem's clothes. As of 18 Aug: 346 open issues, of which 126 (36%) are already epic children and 283 have no milestone. So the 14-child epic wasn't the cause — a third of the list was epic children before it existed. And the milestone page only ever showed the ~63 issues that carried a milestone; the other 283 were unreachable that way.

Milestone pages felt better for one reason: they were the only scoped view anyone had built. is:issue is:open -has:parent-issue gets you to 220 instead of 346 and costs nothing. parent-issue:konvoy-kegs/konvoy#5835 gets you one epic's 13 children. Both were available the whole time.

The general lesson: when a list is unmanageable, build a view before you invent structure. Structure invented to solve a view problem — a project per epic, a milestone per sprint — is permanent, has maintenance cost, and doesn't actually fix the list.

Why iterations beat sprint milestones

Three reasons, in order of how much time they save you:

  • They auto-advance. Unfinished work rolls forward visibly instead of needing a manual M24→M29 sweep. That sweep is the thing you asked for by hand, and it's the thing that silently doesn't happen when you're busy.
  • They free the milestone field for its actual job. While M## occupied it, an epic and a sprint were competing for the same slot on the same issue. That competition is why the epic milestones looked like a workaround.
  • @current is a stable filter. A view filtered on sprint:@current never needs editing. A view filtered on milestone:"M29 - August 17 - 28" needs editing every fortnight, forever, and silently shows the wrong sprint if you forget.

The cost is that iterations are project-scoped, so they don't appear on the repo issue list. That's the trade: you look at the board for time, and at the repo for scope.

Why an issue type rather than a label

Labels are cheap, which is exactly the problem — anyone can add one, nobody has to, and there's no validation. label:epic currently finds 8 issues while 27 have sub-issues, so the label is already lying by a factor of three. An issue type is a single-value field on a controlled org-level vocabulary; it shows in the issue header, it's filterable as type:Epic, and it can't drift into Epic / epic / EPIC. The label trim from 29 to 22 in July was the same instinct — fewer, more meaningful axes.

Why this runbook exists separately from the hygiene runbook

The hygiene runbook answers "what do I do this week". This one answers "why is the board shaped like this". They rot at different rates: hygiene changes when the team changes, configuration changes when the tooling does. Keeping them apart means a GitHub feature release doesn't invalidate your Monday checklist, and a fourth developer doesn't invalidate your field model.

It also means the field model is written down somewhere other than your head — which is the whole point. The next person who asks "should I set the milestone on the PR too?" gets the table at the top of this document instead of twenty minutes of your Monday.

Anti-patterns to watch for

  • Re-adding an M30 milestone out of habit. The muscle memory is strong and the cost isn't visible for a fortnight. Decision 1 exists to force the moment.
  • Hand-editing a view filter to include specific issue numbers. Any filter containing an issue number is a filter that will be wrong next month. Group instead.
  • Setting Sprint on a PR. PRs inherit their timing from the issue they close. If a PR needs a sprint, the issue is missing.
  • Treating "unresolved" in the Decisions tab as harmless. Decision 2 is currently costing 40% of PR field entry. Unresolved means still paying.
